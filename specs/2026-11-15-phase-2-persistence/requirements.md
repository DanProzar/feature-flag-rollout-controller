# Phase 2 — Persistence: Requirements

Branch: `feature/phase-2-persistence`
Roadmap: `specs/roadmap.md` → Phase 2, items 14–20 (item 20 extended with users and cohorts
repositories and seeded cohorts and flags, see "Decisions").
Status: ✅ Complete — merged 2026-11-15. Historical record, frozen at merge; the current truth is `specs/mission.md` and `specs/tech-stack.md`. Later changes: audit `after` became nullable
for deletes (Phase 4); the audit index became `{ key, at, _id }` and the assignments fallback
tolerates a removed winner (Phase 7).

## Context

Phase 0 delivered a containerised Next.js skeleton with a `mongo` compose service; Phase 1 delivered
the pure evaluator in `src/domain` (`evaluate`, `bucket`, `Clock`). The evaluator takes a
`Flag | null` and an optional stored sticky value, and returns `persist: true` when the result must
be stored — but nothing loads or stores anything yet.

This phase builds `src/data`: small MongoDB repositories that load the evaluator's inputs and store
its outputs, plus the audit log, the test reset and seed data (cohorts, users, flags) that later
phases — the admin UI and the Phase 6 demo page — can be tried against. Phase 3's route handlers will only
compose these functions with `evaluate`. Per the mission's "Correctness first" and "Deterministic &
explainable" principles, every repository is covered by integration tests against a real MongoDB,
and sticky writes are proven race-safe (the guarantee that makes sticky assignments trustworthy).

## Scope

All code lives in `src/data`; tests in `src/data/tests/*.int.test.ts` (integration) and
`src/data/tests/*.test.ts` (unit, no Mongo).

1. **Config** (`src/data/config.ts`, item 14)
   - `loadConfig(env = process.env): { mongodbUri: string; mongodbDb: string }`, parsed with Zod;
     throws a readable error when `MONGODB_URI` or `MONGODB_DB` is missing or empty.
2. **Client singleton** (`src/data/client.ts`, item 14)
   - `getDb(): Promise<Db>` lazily creates one `MongoClient` from `loadConfig()` and caches the
     connecting promise on `globalThis` (survives Next.js dev hot reloads; concurrent callers share
     one connection).
   - `closeDb(): Promise<void>` closes it and clears the cache (used by the seed CLI and tests).
3. **Indexes** (`src/data/indexes.ts`)
   - `ensureIndexes(db)`: idempotent; creates
     - `flags`: unique `{ key: 1 }`
     - `assignments`: unique `{ flagKey: 1, userId: 1 }`
     - `audit`: `{ key: 1, at: 1 }`
     - `users`: unique `{ userId: 1 }`
     - `cohorts`: unique `{ key: 1 }`
4. **Document schemas** (`src/data/schemas.ts`)
   - Zod schemas for every stored document (`flags`, `assignments`, `audit`, `users`, `cohorts`).
     Every document read from MongoDB is parsed with them before being returned; a malformed
     document throws.
5. **Flags repository** (`src/data/flags.ts`, item 15) — `createFlagsRepository(db, clock)`:
   - `get(key): Promise<Flag | null>` — domain `Flag` (the six mission fields), storage metadata
     stripped.
   - `upsert(flag: Flag): Promise<Flag | null>` — full replace of the five mutable fields by `key`;
     sets `updatedAt = clock.now()` always and `createdAt = clock.now()` only on insert; returns the
     **previous** `Flag`, or `null` when it was created.
6. **Assignments repository** (`src/data/assignments.ts`, items 16–17) —
   `createAssignmentsRepository(db, clock)`:
   - `get(flagKey, userId): Promise<boolean | undefined>` — the stored value, or `undefined` when
     there is none (fits `evaluate`'s `stickyValue?` parameter directly).
   - `insertIfAbsent(flagKey, userId, value): Promise<boolean>` — upsert with `$setOnInsert`
     (`value`, `createdAt = clock.now()`) on the unique index; returns the value **actually stored**
     (the first writer's). A duplicate-key error from a concurrent upsert is caught and resolved by
     re-reading.
7. **Audit repository** (`src/data/audit.ts`, item 18) — `createAuditRepository(db)`:
   - `append(entry: AuditEntry): Promise<void>` where
     `AuditEntry = { at: Date; key: string; actorId: string | null; before: Flag | null; after: Flag }`.
     The caller supplies every field (Phase 3 takes `at` from the clock and `before` from
     `flags.upsert`).
   - `listByKey(key): Promise<AuditEntry[]>` — oldest first (`at` ascending, then insertion order);
     empty list for an unknown key.
8. **Reset** (`src/data/reset.ts`, item 19)
   - `resetFlagsAndAssignments(db): Promise<void>` — deletes all documents in `flags` and
     `assignments`. `audit` and `users` are untouched; indexes are kept.
9. **Users repository** (`src/data/users.ts`, item 20 + extension) — `createUsersRepository(db)`;
   `User = { userId: string; name: string; cohorts: string[] }`:
   - `userId` is a **UUID v7** generated by the `uuid` library (`v7()`); the document schema checks
     it with `uuid`'s `validate` and `version() === 7`.
   - `get(userId): Promise<User | null>`
   - `list(): Promise<User[]>` — sorted by `userId` (i.e. creation order, since v7 is
     time-ordered).
   - `create({ name, cohorts }): Promise<User>` — generates the `userId`; callers cannot choose it.
   - `update(user): Promise<User | null>` — full replace of `name` and `cohorts`; `null` if missing
     (never creates).
   - `delete(userId): Promise<boolean>` — `true` if a user was removed.
   - `clear(): Promise<void>` — deletes all users (which also re-enables seeding users, see below).
10. **Cohorts repository** (`src/data/cohorts.ts`, item 20 + extension) —
    `createCohortsRepository(db)`; `Cohort = { key: string; name: string; description: string }`:
    - Same operations as users, keyed by a caller-chosen `key` (not a UUID): `get`, `list` (sorted
      by `key`), `create(cohort)` (throws `DuplicateCohortError` if `key` exists), `update` (full replace of `name` and `description`,
      `null` if missing), `delete`, `clear`.
    - **Reference only**: users and flags keep storing cohort keys as plain strings; nothing
      validates them against this collection, and the evaluator is unchanged. It is a catalogue for
      UIs.
11. **Seed** (`src/data/seed.ts`, `src/data/seed.cli.ts`, item 20)
    - `SEED_COHORTS`: `admin`, `tester`, `user`, `developer`, each with a display name and a short
      description.
    - `SEED_USERS`: 6 users over those cohorts; every cohort used at least once, some users in
      several. Their `userId`s are **fixed UUID v7 constants** (generated once, committed as
      literals) so bucketing — and therefore the demo — is the same on every fresh database. They
      are inserted directly with these IDs, not through `users.create`:

      | userId | name | cohorts |
      |--------|------|---------|
      | `01a1dc80-f000-7ca2-9842-a25ac04f528a` | Alice | `admin`, `developer` |
      | `01a1dc80-f001-7d40-8f31-97b3a953464b` | Bob | `tester` |
      | `01a1dc80-f002-7f7b-8e7c-8b8f50312ce4` | Carol | `user` |
      | `01a1dc80-f003-7c9f-bae4-c766892e83f6` | Dan | `developer` |
      | `01a1dc80-f004-7407-835c-df1b0df5d2fd` | Eve | `user`, `tester` |
      | `01a1dc80-f005-7503-bf21-c2146a512485` | Frank | `user` |

    - `SEED_FLAGS`: 5 flags, together producing every evaluation reason against the seed users
      (and matching the features of the Phase 6 demo page):

      | key | enabled | percentage | includeCohorts | excludeCohorts | sticky | Shows |
      |-----|---------|-----------|----------------|----------------|--------|-------|
      | `new-checkout` | `true` | 50 | — | — | `true` | `PERCENTAGE`, then `STICKY` |
      | `dark-mode` | `true` | 0 | `tester`, `developer` | — | `false` | `COHORT_INCLUDED` |
      | `beta-search` | `true` | 100 | — | `user` | `false` | `COHORT_EXCLUDED` |
      | `legacy-banner` | `false` | 100 | — | — | `false` | `KILL_SWITCH` |
      | `ai-assistant` | `true` | 35 | `admin` | — | `false` | `PERCENTAGE`, `COHORT_INCLUDED` |

      (`FLAG_NOT_FOUND` is shown by asking for any unseeded key.) With the seed users' buckets,
      `new-checkout` is on for Bob (30), Carol (27), Dan (15) and Eve (14) and off for Alice (87)
      and Frank (69); `ai-assistant` is on for Bob (16) and Carol (5) by percentage, for Alice by
      cohort, and off for Dan (69), Eve (64) and Frank (51).
    - `seed(db, clock): Promise<SeedResult>` where
      `SeedResult = Record<"cohorts" | "users" | "flags", { seeded: boolean; count: number }>`.
      Each collection is handled **independently**: its seed data is inserted only when that
      collection is empty; otherwise it is left alone and reported `{ seeded: false, count: 0 }`. A
      concurrent seed that loses the race (duplicate key) also reports `seeded: false`.
    - Flags are written through the flags repository (`createdAt`/`updatedAt` from `clock`) and
      **no audit entries** are written — the audit log only records real admin changes.
    - Because `resetFlagsAndAssignments` empties `flags`, the next seed run repopulates the seed
      flags; cohorts and users are untouched by reset, so they are not re-seeded.
    - `seed.cli.ts`: `loadConfig` → `ensureIndexes` → `seed(db, systemClock)` → logs one line per
      collection (`seeded N cohorts` / `cohorts already present, skipping`, likewise for users and
      flags) → closes the client → exit `0`; any error → exit `1`.
    - `npm run seed` runs the CLI with `tsx`, loading `.env` if present.
    - Compose: a one-shot `seed` service (built from a new `seed` Dockerfile stage with sources and
      dev dependencies) runs `npm run seed` after `mongo` is healthy; `app` depends on it with
      `condition: service_completed_successfully`.
12. **Barrel** `src/data/index.ts` re-exporting the public API.
13. **Tooling**
    - Dependencies: `zod`, `mongodb`, `uuid` (runtime); `tsx` (dev).
    - Vitest projects: `unit` (`src/**/*.test.ts` minus `*.int.test.ts`) and `int`
      (`src/**/*.int.test.ts`).
    - Scripts: `test` (unit only, no Mongo needed), `test:int`, `test:all`, `test:coverage` (all
      projects, needs Mongo), `seed`.
    - `docker-compose.dev.yml` maps `mongo` port `27017:27017` so host tests can reach it.
    - Test harness `src/data/tests/harness.ts`: `useTestDb()` connects to
      `MONGODB_URI ?? "mongodb://localhost:27017"`, uses a unique database
      `feature_flags_test_<random>` per test file, runs `ensureIndexes`, provides a helper to empty
      collections between tests, and drops the database and closes the client in `afterAll`.

## Out of scope

- Zod request schemas, route handlers, reset endpoint, swapping the app clock, audit-on-PUT wiring
  (Phase 3). This phase provides the functions; nothing calls them from HTTP yet.
- Calling `ensureIndexes` on app startup (Phase 3, alongside the first route handler).
- Users and cohorts API/UI — both repositories are data-layer only for now.
- Validating cohort keys on users or flags against the `cohorts` collection.
- The `/demo` page (mock product UI + user switcher → flag grid). It is added to the roadmap as
  Phase 6, after Polish, and will call the real evaluate API; this phase only provides its seed
  data.
- Flag `description` field, deleting flags, environments, auth (mission non-goals / later).
- Any UI (Phase 4).

## Decisions

| Topic | Decision | Rationale |
|-------|----------|-----------|
| Branch | Reuse existing `feature/phase-2-persistence` | Already holds the roadmap commit moving the seed step into Phase 2. |
| Repository shape | **Factories taking `Db` (+ `Clock` where timestamps are written)** | Tests pass a per-file `Db` and `frozenClock`; Phase 3 wires them to the singleton and the app clock. |
| Flag mapping | **Domain `Flag` in/out**; `createdAt`/`updatedAt` stored but stripped on read | The evaluator and the audit `before`/`after` speak `Flag`; no extra mapping in Phase 3. |
| Read validation | **Zod-parse every document read** | Corrupted or hand-edited documents fail loudly at the boundary instead of reaching the evaluator. Adds `zod` now (needed in Phase 3 anyway). |
| Upsert timestamps | `findOneAndUpdate` with `$set` (five fields + `updatedAt`) and `$setOnInsert` (`key`, `createdAt`), `returnDocument: "before"` | Full-replace semantics for the flag fields while preserving `createdAt`; returns the previous value atomically for the audit. |
| Sticky race safety | Upsert + `$setOnInsert` on the unique index; on `E11000` re-read and return the stored value | First write wins and every concurrent caller returns the same value (`tech-stack.md`). |
| Audit API | **Caller passes the full entry** | Repo stays a dumb append/list; timing and `before` come from the API layer that owns them. |
| Indexes | **Explicit `ensureIndexes(db)`** | One idempotent place, called by the seed CLI and test harness now, by app startup in Phase 3. |
| Seed guard | Seed **each collection only when it is empty**, independently; a run with nothing to do is a **no-op, exit 0** | Seed runs once per collection; `docker compose up` keeps working on restarts. |
| Clearing / reset | `users.clear()` / `cohorts.clear()` re-enable seeding that collection; reset empties `flags`, so the seed flags come back on the next seed run | Follows from the empty-collection guard; no separate marker needed. |
| Users CRUD | `get`/`list`/`create` (generates the id)/`update` (full replace, `null` if missing)/`delete`/`clear` | Requested extension of item 20; mirrors the full-replace style of flags. |
| User IDs | **UUID v7 from the `uuid` library**, generated in `users.create`; no `DuplicateUserError` | Callers can't pick or collide IDs; v7 is time-ordered, so `list()` returns users in creation order. |
| Seed user IDs | **Fixed UUID v7 constants** | Random IDs would change who falls into each percentage bucket on every fresh database, making the demo and seed tests non-deterministic. |
| Cohorts | **`cohorts` collection, reference only**, with the same CRUD as users | Gives UIs a catalogue of cohorts without changing the evaluator, the `Flag` shape or the PUT contract. |
| Seed flags | 5 flags, one per evaluation reason, written **without audit entries** | Every rule can be seen against the seed users; the audit log only reflects real admin changes. |
| Demo page | `/demo` **inside the existing app**, mock product UI + user switcher → flag grid, as **Phase 6 after Polish** | Exercises the finished API like a real client; out of scope here. |
| Seed in compose | One-shot `seed` service from a `seed` Dockerfile stage; `app` waits for it | The standalone runtime image has no sources or `tsx`; keeps seeding out of app startup. |
| Test Mongo | Compose `mongo` with port exposed in `docker-compose.dev.yml` | No extra dependency; same Mongo version as runtime. |
| Isolation | **Unique database per test file**, dropped in `afterAll` | Files run in parallel without interfering. |
| Test scripts | Split `test` (unit) / `test:int` / `test:all` | `npm test` stays fast and needs no Mongo. |
| Coverage | 100% on `src/data` (excluding `tests/`, `index.ts`, `seed.cli.ts`) and keep 100% on `src/domain` | Same bar as Phase 1; the CLI is a thin wrapper verified manually. |
